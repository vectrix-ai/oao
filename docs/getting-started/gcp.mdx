---
title: "Deploy to Google Cloud"
description: "Release OAO to the development Cloud Run service and worker pool without giving application CI control of infrastructure."
---

OAO's development deployment uses one immutable container image in Artifact
Registry. Terraform owns the Cloud Run service, worker pool, Cloud SQL
attachment, runtime identities, IAM, scaling, probes, environment variables,
and secret references. The OAO repository owns application tests, image builds,
and image-only releases.

## Required repository variables

Configure these repository variables after Terraform has created the resources.
The protected `oao-dev` environment remains the deployment approval boundary;
do not put these values only in that environment, because the workflow decides
whether a release is enabled before protected-environment setup:

```text
GCP_PROJECT_ID
GCP_REGION
GCP_ARTIFACT_REGISTRY_REPOSITORY
GCP_WORKLOAD_IDENTITY_PROVIDER
GCP_RELEASE_SERVICE_ACCOUNT
CLOUD_RUN_SERVICE
CLOUD_RUN_WORKER_POOL
OAO_DEV_RELEASE_ENABLED
```

Keep repository variable `OAO_DEV_RELEASE_ENABLED` set to `false` for the
first merge. The workflow builds and pushes the bootstrap image without
attempting to update Cloud Run.
After Terraform creates both workloads, set it to `true` so pushes to `main`
perform image-only releases.

The release identity uses GitHub OIDC. Do not add service-account keys, database
passwords, or other secret payloads to GitHub Actions.

## Release

Pushing to `main` runs the workspace checks, builds a Node 22.19/pnpm 10.27
image, pushes it under the commit SHA, resolves its Artifact Registry digest,
and releases that same digest to both workloads. The API runs the image's
default `api` command; the worker pool uses its `worker` command.

The release workflow changes only each workload's image field. It verifies the
image belongs to this repository, waits for both new revisions to become ready,
checks their digests, and calls the private API `/readyz` endpoint with a
short-lived Google OIDC identity token. It records the previous immutable image
references and automatically restores both workloads when a later release step
fails. An incomplete rollback is surfaced as an explicit workflow error for
operator intervention.

To redeploy a known-good build, run **Deploy GCP dev** manually and provide its
full digest reference, for example:

```text
europe-west1-docker.pkg.dev/example-project/oao/oao@sha256:...
```

Use only an image digest, never a mutable tag such as `latest`.

## One-time database and identity setup

The DEV pilot keeps the Cloud Run service private and uses OAO development
auth behind Cloud Run IAM while the team evaluates IAP and WorkOS. Grant only
explicit callers `roles/run.invoker`; callers must send a Google OIDC identity
token whose audience is the Cloud Run service URL in the
`X-Serverless-Authorization` header. OAO keeps the standard `Authorization`
header for its own API keys. Browser login is deferred until an identity
provider is selected.

Generate `oao-credential-encryption-key` as the canonical base64 encoding of
exactly 32 random bytes (`openssl rand -base64 32`). Generate a separate random
`oao-api-key-pepper`. Store both only as Secret Manager versions outside
Terraform and never commit their payloads.

For this disposable DEV pilot only, set a password on Cloud SQL's built-in
`postgres` user outside Terraform. Both application processes auto-migrate, so
they temporarily share this admin-capable credential. Do not carry this into
UAT or production; separating migrator and runtime identities is deferred.
Store the runtime Unix-socket URL only as a version of `oao-database-url`:

```text
postgresql://postgres:ENCODED_PASSWORD@localhost/oao?host=/cloudsql/PROJECT:REGION:INSTANCE
```

URL-encode reserved password characters; never put the URL in Git or Terraform.

Before the first login, run Cloud SQL Auth Proxy locally on
`127.0.0.1:5432`. From the `oao-tf/environments/dev` root, read the exact
connection name from Terraform and start the proxy:

```sh
CLOUD_SQL_CONNECTION_NAME="$(terraform output -raw cloud_sql_connection_name)"
cloud-sql-proxy --address 127.0.0.1 --port 5432 "$CLOUD_SQL_CONNECTION_NAME"
```

In a second shell, use its TCP URL to migrate and idempotently seed the
disposable DEV tenant:

```sh
DATABASE_URL=postgresql://postgres:ENCODED_PASSWORD@127.0.0.1:5432/oao \
pnpm --filter @oao/api seed:dev
```

The seed creates organization `00000000-0000-4000-8000-000000000001`, project
`00000000-0000-4000-8000-000000000002`, and owner principal
`00000000-0000-4000-8000-000000000003`. All IAM-authorized callers share that
development identity during the pilot; this is not suitable for production or
per-user auditing.
