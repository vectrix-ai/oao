---
title: Releases
description: How OAO versions and releases the platform from main.
---

OAO uses Release Please to maintain one platform version across the monorepo.
Every push to `main` runs the release workflow. Release Please reads the
Conventional Commits merged since the last release and creates or updates one
release pull request.

## Version changes

Pull requests targeting `main` should use a Conventional Commit title (checked
by the **Pull request title** workflow). Release Please reads the commit
messages that land on `main`, so squash-merge using the validated Conventional
Commit PR title as the commit subject (or ensure the landed commit(s) carry a
Conventional Commit prefix; retitle GitHub revert PRs to `revert: ...`).

Every recognized Conventional Commit type is releasable on its own and
contributes to the next rolling release proposal in `CHANGELOG.md`:

| Prefix                                                                                                     | Version effect                | Example                                     |
| ---------------------------------------------------------------------------------------------------------- | ----------------------------- | ------------------------------------------- |
| `fix:`, `perf:`, `revert:`, `deps:`, `chore:`, `docs:`, `build:`, `ci:`, `refactor:`, `test:`, or `style:` | Patch                         | `chore(deps): refresh weekly dependencies`  |
| `feat:` or `feature:`                                                                                      | Minor                         | `feat: add project-scoped model presets`    |
| `feat!:` (or any type with `!`) or a `BREAKING CHANGE:` footer                                             | Minor (`0.x`), Major (`1.0+`) | `feat!: replace the session event envelope` |

Dependency-only updates (`chore(deps):`, `deps:`, `fix(deps):`), documentation
changes, test updates, build/CI changes, and other chores can each trigger a
patch version increment on their own. When multiple pull requests merge before
the rolling release pull request is published, Release Please batches them into
one version increment calculated from the accumulated commits since the last
release.

The repository starts from `0.0.0`. While on `0.x`, breaking changes increment
the minor version (`bump-minor-pre-major: true` in `.release-please-config.json`);
from `1.0.0` onward they increment the major version. Release Please updates the
root `package.json`, every workspace package version, the MCP server's advertised
version, the version manifest, and `CHANGELOG.md` together.

## Publishing a release

Review and merge the `chore: release x.y.z` pull request when the accumulated
changes are ready to publish. The next workflow run creates the `vx.y.z` tag
and matching GitHub release. Until that pull request is merged, later changes
to `main` update the same release proposal.

`main` is protected by a repository ruleset: changes must arrive through a pull
request, force pushes are blocked, and the branch cannot be deleted. The release
workflow writes only to its release branch and never bypasses this protection.
